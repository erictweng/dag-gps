# DAG GPS v1 Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task; if unavailable, use a fresh implementation worker followed by parent spec-compliance and code-quality verification. This document is planning only, not authorization to start implementation.

**Goal:** Eric can orient himself in a supported repository, understand a feature, inspect potential change impact, correct lookup vocabulary, and refresh the map without assistant intervention or misleading claims.

**Architecture:** Keep the pinned Git archive → validated map/evidence → standalone offline HTML pipeline. Add deterministic impact analysis, explicit evidence-quality metadata, a local layer-map authoring loop, and opt-in evaluation records; preserve the local Jev-style operation/target chooser and graph router.

**Tech Stack:** Python stdlib build tools; dependency-free browser/Node JavaScript; SVG UI; unittest/node:test; Playwright for browser verification. No accounts, hosted inference, or browser network dependency.

## 2. Scope and release boundary

v1 means a dependable architecture navigator for the explicitly supported TS/JS/Python repositories, not universal code understanding. An unsupported construct is a visible limitation, not a reason to fake completeness.

Out of scope: trained local model, free-form LLM explanations, automatic tour generation, execution/coverage tracing, change application, live watcher, IDE plugin, cloud sync, accounts, collaboration and backend hosting. No schedule promise before the initial scope gate. Additions discovered during work become post-v1 backlog unless they block an acceptance criterion.

## 3. Order and dependencies

V1.0 baseline/acceptance contract → V1.1 impact → V1.2 trust → V1.3 onboarding → V1.5 release.
V1.4 real-query evaluation starts immediately after V1.0 and runs alongside the sequence, but changes to shared scorer/UI files remain serialized. V1.1 begins using existing evidence and conservative labels; V1.2 improves precision without delaying the first useful impact preview.

### V1.1 — Explainable change-impact previews

**Deliverable:** choose a FILE and see direct/transitive consumers, dependency-linked tests, tour references, and a reason chain for every inclusion.

**Likely files:** create `web/impact.js`, `tests/impact.test.cjs`, `scripts/smoke_impact.cjs`; modify `web/template.html`, `scripts/render.py`, `web/tour-ui.js` only as necessary; add `docs/IMPACT_REPORT.md`.

**Mini 1.1a — Pure analysis:**
- Add `analyzeImpact(map, tours, fileId)` returning direct consumers, transitive consumers, test candidates, affected tour references, evidence chains and limitations.
- Reverse **import** edges by default. Explicit HTTP/RPC links appear in a separately labeled potential boundary-impact section, never indistinguishably mixed with import reachability. Ignore realtime for default traversal.
- BFS visited set terminates cycles; deterministic ordering and shortest witness chains. Recognize test nodes through explicit build classification or documented path rules, not filename guessing alone.
- Affected tours means citations referencing that file, not proof the narrative broke.
- With no observed test connection show 'coverage unknown', never 'untested'.

**Mini 1.1b — UI and Ask:**
- 'Inspect potential impact' on file details plus explicit impact Ask pattern. Ambiguous lookup requires choice before analysis.
- Show Direct / Transitive / Linked tests / Tour references; click result reveals inclusion chain and real node.
- Legend says potential impact, no guarantees. Keep dependency direction explicit and legacy Ask intact.

**Gate:** fixture assertions for cycles, direct/transitive distinctions, unknown IDs, isolated files, HTTP separation and tour references; two real-file browser checks with source-backed witness chains. Example initial target `lib/runner-client.ts`; audit graph to establish expectations before tests, do not fabricate test reachability.

### V1.2 — Map trust and completeness

**Deliverable:** a user can see evidence provenance, extraction scope and blind spots at the place where they affect an answer.

**Likely files:** `scripts/import_graph.py`, `scripts/build_map.py`, `scripts/build_project.py`, `scripts/tours.py`, `web/impact.js`, `web/template.html`, `tests/test_refresh.py`; create `tests/test_extraction_trust.py`, `scripts/smoke_trust.cjs`, `docs/TRUST_REPORT.md`.

**Mini 1.2a — Trust contract:**
- Normalize diagnostic categories: resolved source link, non-source target, unresolved local reference, unsupported dynamic construct, external dependency.
- Keep extraction evidence and manually curated runtime evidence separate. Report scope denominator/file counts, not unsupported claims such as '95% runtime completeness'.
- UI findings panel with path and concrete reason; answer/impact limitation badge uses relevant findings when traceable, otherwise reports repo-level uncertainty.

**Mini 1.2b — Narrow extraction fixes:**
- Improve static relative Python imports and any verified high-impact CommonJS/TS cases identified at baseline. Regression fixture first; no full parser dependency unless approved.
- Legitimate source cycles are represented, not deleted to make a DAG gate green. If stronger extraction reveals layer cycles, report for layer review or implement SCC display only with an explicit decision.
- Refresh may legitimately alter old edges. Version/report extraction changes and regenerate expected snapshot deliberately rather than weakening parity assertions.

**Mini 1.2c — Stale-tour handling:**
- Preserve current fail-closed exact-commit tour validation.
- Refresh without stale tours must be an explicit opt-out, showing tours unavailable; never silently attach old citations or auto-edit narrative.

**Gate:** known blind spots reproduced in fixtures, diagnostics truthful, stale tour mismatch leaves prior output unchanged, runtime/import distinction visible in browser. Frozen legacy extractor tests retained or migrated with documented evidence.

### V1.3 — Reviewable repo onboarding

**Deliverable:** add a supported repo without hand-writing layer JSON; a human reviews the grouping before publication.

**Likely files:** create `scripts/draft_layers.py`, `web/layer-editor.js`, `web/layer-editor.html`, `scripts/render_layer_editor.py`, `tests/test_draft_layers.py`, `tests/layer-editor.test.cjs`, `scripts/smoke_onboarding.cjs`; modify `scripts/build_project.py`, map validators, README.

**Mini 1.3a — Draft:**
- Deterministic folder-based groups with explicit handling for flat roots and shared helpers; no LLM or claims of architectural truth.
- Record file list, proposed ownership and reasons. Prefer correctness of coverage to attractive grouping.

**Mini 1.3b — Offline review:**
- Rename/merge/split layers, reassign files, search paths; show coverage, duplicate assignments and layer cycles.
- Browser downloads corrected JSON; it cannot directly write repo files. Export then rerun builder.
- Preserve stable layer IDs for a rename, warn about alias/tour references on deletion/split; no guessing migrations.

**Mini 1.3c — Publish round trip:**
- draft → review → export → validated build. Clear actionable rejection for unsupported import structures.
- Two real repos: quest-coder plus DAG GPS. Self demo should target an explicit newer supported snapshot, not pretend pre-feature snapshot is current.

**Gate:** second real repo onboarding without manually editing JSON; no missing/double-assigned files; invalid export/assignment doesn't replace published output. User reviews high-level meaning; automatic grouping is never final by default.

### V1.4 — Opt-in real-query evaluation (parallel track)

**Deliverable:** Eric can record useful failures and corrected answers locally, export a labeled regression set, and see measured tradeoffs.

**Likely files:** create `web/query-feedback.js`, `scripts/eval_user_queries.cjs`, `tests/query-feedback.test.cjs`, `scripts/smoke_feedback.cjs`; modify `web/template.html`, `web/scorer.js` only for verified general fixes; add `docs/USER_EVAL_REPORT.md`.

**Mini 1.4a — Capture:** logging OFF by default. Explicit enable; Correct / Wrong / Unclear with editable expected operation/node; snapshot and alias-overlay provenance. Remove/clear/export controls; local only, no telemetry.

**Mini 1.4b — Evaluate:** distinguish user-authored, generated, development and held-out cases. Report accepted wrong answers, unnecessary abstentions, top1/top3, no-path truth, and p95 scorer latency separately from UI rendering. No re-labeling a miss to improve metrics.

**Mini 1.4c — Improve:** preserve a held-out user subset before tuning; fix broad matching rules instead of memorizing exact questions. Test alias-off and alias-on results separately.

**Gate:** consent/privacy/import validity browser checks; ideally 20 or more Eric-authored queries. Missing real queries does not block implementation but blocks claims of real-user accuracy. Existing actual `runner.py` feedback can seed a case only if Eric confirms intended target; do not invent his intent.

### V1.5 — Release, usability and performance

**Deliverable:** reproducible v1 offline artifacts and a documented complete workflow; no P0/P1 defects.

**Likely files:** README, `docs/V1_ACCEPTANCE.md`, `docs/V1_RELEASE.md`, `scripts/release_check.py`, `.verify.json`, layout/accessibility CSS, focused regression tests.

**Mini 1.5a — Full-session audit:** find → inspect → tour → impact → correct alias → export → edit grouping → refresh → import. Run on both supported demos; no overlapping controls, stale highlights, impossible recovery or misleading evidence.

**Mini 1.5b — Scale and accessibility:** verify 1280/1920 desktop, graceful 390px layout; keyboard/focus/Escape, contrast, accessible names, reduced motion. Benchmark declared real graphs plus clearly labeled synthetic 1k/5k-node fixtures. Keep warm scorer p95 target under 10ms on recorded hardware; measure cold initialization, layout time and full Ask independently, never call scorer latency end-to-end latency. Virtualize/limit file views if needed rather than shrink text unreadably.

**Mini 1.5c — Release:** stable CLI examples, supported-source limitations, dependency/test setup, local storage/export recovery, pinned source/tour regeneration guide and versioned artifact manifest. Check outputs reveal private code excerpts before sharing; no automatic public upload.

**Gate:** all milestone acceptance tests and legacy gates pass; no external browser requests; malformed imports remain data, not executable code; immutable source evidence verified; build failure keeps prior artifacts; no silent learning. Eric completes one real repo workflow without operational assistance. If user playtest is pending, label release candidate, not v1 complete.

## 5. Execution procedure per mini-milestone

1. Parent inspects current git/source state, checks prior gate and sets narrow worker handoff with allowed files.
2. Worker writes a regression that fails before the change; records failure; implements minimal change; runs focused tests then full relevant recipes.
3. Parent reviews spec compliance then code quality, independently reruns checks, inspects browser evidence and validates scope. A worker 'done' is not acceptance.
4. Commit verified mini-milestone, integrate fresh main without clobbering concurrent work, push authorized direct-to-main, read back remote SHA.
5. Update STATUS/TASKS/report and next action; send meaningful stage updates in build channel. Stop before next milestone if a product decision or unverified gate remains.

Exact existing gate examples (run from repo root; future files named above are proposals):
```sh
python3 -m unittest discover -s tests -q
node --test tests/*.test.cjs
node scripts/eval_scorer.cjs
node scripts/eval_lookup.cjs
node scripts/eval_alias.cjs
node scripts/smoke_tours.cjs
```
Use the current `.verify.json` non-null recipes for builds/full smoke; preserve pinned snapshot/tour requirements. Future dedicated smoke scripts are added as features land, never describe them as currently available.

## 6. Risks and proposed defaults to approve

- Desktop-first offline HTML remains primary; phones gracefully support inspection, not an equally powerful full authoring experience.
- Impact default is static import evidence; typed runtime/boundary relationships are disclosed separately. No execution/coverage inference.
- Query feedback capture off by default and local only. No server/storage service.
- Onboarding requires human review and download/rebuild; not a web app that edits the filesystem.
- A supported-source limitation list beats a universal-language promise. Expanding language coverage is post-v1 unless a real supported repo blocks.
- v1 acceptance needs a user session, not just green automated tests. No fixed dates or estimates until V1.0 baseline and scope approval.
